# Kesha integration audit

Дата аудита: 2026-10-28  
Исходный проект: `C:\projects\jarvis-kesha`  
Целевой проект: `C:\projects\Jarvis`

## Итог до переноса

В исходном проекте не обнаружена отдельная обученная voice-cloning/TTS-модель
Кеши. Проект представляет собой ранний голосовой ассистент, в котором:

- распознавание выполняется локальной моделью Vosk;
- синтез выполняется стандартным Silero TTS `ru_v3`;
- выбранный в коде диктор Silero — `aidar`;
- отдельные персональные веса голоса Кеши, reference-аудио для voice cloning,
  конфигурация VITS/XTTS или самостоятельный Kesha inference engine отсутствуют.

Поэтому копирование `model_small/ru_v3.pt` не перенесло бы голос Кеши: это
часть ASR/Vosk-модели, а не TTS. Называть стандартный Silero `aidar` обученным
голосом Кеши нельзя.

## 1. Архитектура исходного проекта

`jarvis-kesha` — монолитный Python-скрипт:

- `main.py` — wake word Porcupine, Vosk ASR, сопоставление команд из
  `commands.yaml`, запуск `.exe`/команд Windows и ветвление на ChatGPT;
- `tts.py` — ленивого адаптера нет: Silero загружается при импорте через
  `torch.hub.load('snakers4/silero-models', model='silero_tts',
  language='ru', speaker='ru_v3')`;
- `tts.py` вызывает `apply_tts(... speaker='aidar', sample_rate=48000)` и
  проигрывает результат через `sounddevice`;
- `model_small/` — локальная малая русская Vosk-модель ASR;
- `sound/` — заранее записанные WAV-ответы для команд;
- `custom-commands/` — AHK/EXE-команды Windows.

Самостоятельного HTTP/API-сервера или отдельного inference-процесса в исходном
проекте нет. `main.py` работает как один процесс ассистента.

```python

    model='silero_tts',
    language='ru',
    speaker='ru_v3',
)
```

`C:\Users\Данил\.cache\torch\hub\snakers4_silero-models_master\src\silero\model\ru_v3.pt`
размером 59,199,351 байт. Это кэш стандартного Silero, а не артефакт,
обученный внутри `jarvis-kesha`.

### Что не найдено

Не найдено: Kesha-specific checkpoint, VITS/XTTS config, speaker encoder,
reference dataset, tokenizer/phoneme dictionary для персонального TTS,
vocoder, локальный Kesha server или отдельный inference runner.

`dev.env` содержит секрет Picovoice и не должен переноситься в Jarvis или
публиковаться. Секреты из исходного проекта в аудит и поставку не копируются.

## 3. Зависимости и ресурсы

Исходный `requirements.txt` включает `torch`, `torchaudio`, `omegaconf`,
`sounddevice`, `vosk`, `pvporcupine`, `pvrecorder`, `simpleaudio`, `PyYAML`,
`openai`, `pycaw`, `comtypes` и вспомогательные пакеты.

Для фактического синтеза Silero нужны `torch`, `torchaudio`, `omegaconf` и
`sounddevice`; при первом запуске Torch Hub может потребовать сетевой доступ,
если кэш отсутствует. В коде исходника устройство явно задано как CPU.
GPU/CUDA/ROCm не требуется для запуска этого Silero TTS, но CPU-инференс
зависит от длины текста и может быть заметно медленнее GPU.

Загрузка происходит при импорте `tts.py` и модель остаётся в памяти до
завершения процесса. Явного `unload()` нет. Воспроизведение останавливается
через `sd.stop()` при завершении/тайм-ауте.

## 4. Текущая архитектура Jarvis Assist

Целевой проект состоит из FastAPI backend и PySide6 desktop frontend.

- `backend/services/voice_runtime.py` владеет жизненным циклом микрофона,
  Vosk-распознаванием, wake word/последующим диалогом и WAV-ответами;
- `backend/voice_engine/voice_player.py` воспроизводит готовые WAV;
- `backend/voice_engine/tts.py` лениво загружает Coqui XTTS v2 и использует
  `Да сэр.wav` как reference sample;
- `/voice/start`, `/voice/microphone`, `/voice/stop`, `/voice/status` — API
  управления голосовым runtime;
- `frontend/jarvis_ui.py` уже хранит настройки через `QSettings`, перечисляет
  устройства ввода и сохраняет `audio_input_device`;
- настройки “ЗВУК И ВИЗУАЛ” — существующий раздел, куда следует добавлять
  блок голосовой модели без создания второго раздела.

Сейчас в активном runtime нет реестра голосовых моделей и нет persisted
`voice_model_id`; выбор модели нельзя безопасно подключать напрямую к UI.

## 5. Совместимость и безопасное решение

Технически можно интегрировать **точный фактически используемый исходником
Silero TTS** как модель с идентификатором `kesha`, но UI и документация должны
называть её стандартным Silero `ru_v3`, диктор `aidar`, а не обученным голосом
Кеши. Для автономности потребуется перенести локальный Silero checkpoint и
минимальный adapter, либо предусмотреть штатную загрузку из локального
хранилища моделей; зависимость от `C:\projects\jarvis-kesha` при этом не
останется.

Если требуется именно обученный голос Кеши, исходного проекта недостаточно:
нужно предоставить фактический checkpoint и сопутствующие файлы модели либо
разрешить считать стандартный Silero `aidar` временным голосом под именем
Kesha. До такого решения нельзя честно выставлять Kesha как “обученная модель
доступна”.

## 6. План интеграции после подтверждения фактической модели

1. Добавить расширяемый реестр: Jarvis первым и выбранным по умолчанию,
   статус “В разработке/Модель не установлена”; Kesha вторым.
2. Реализовать adapter интерфейса `load / synthesize / health / close`.
3. Добавить проверку локальных ресурсов и реальный smoke-synthesis.
4. Подключить выбор и статус в существующий раздел “ГОЛОС AI”, хранить выбор
   через `QSettings` и передавать его в voice runtime.
5. Не блокировать Qt-интерфейс тяжёлой инициализацией; кэшировать загруженный
   движок и корректно обрабатывать ошибки/нехватку памяти.
6. Провести тесты после перезапуска и отдельно проверить работу при временно
   недоступной исходной директории.
7. Только после отчёта и отдельного подтверждения пользователя можно удалять
   `C:\projects\jarvis-kesha`.

## Текущий вывод

Аудит завершён. Критичная неопределённость — отсутствие в исходном проекте
персональных Kesha TTS-весов. Исходник предоставляет рабочий рецепт
стандартного Silero `ru_v3`/`aidar`, но не подтверждает “обученный голос Кеши”.
Реализация не должна скрывать это различие.

## Реализованный вариант 1

По разрешению пользователя стандартный Silero-профиль подключён под
идентификатором `kesha`. Это именно временный профиль: `ru_v3` с диктором
`aidar`, без утверждения о персональном обучении.

- checkpoint скопирован из локального Torch Hub кэша в
  `backend/voice_engine/models/silero/ru_v3.pt`;
- SHA-256 исходного и целевого файла:
  `BF2BCAB8E814EDB17569503B23BD74E8CC8F584B0D2F7C7E08E2720CC48DC08C`;
- исходный `C:\projects\jarvis-kesha` в runtime не используется;
- каталог моделей исключён из Git, чтобы не добавлять бинарный checkpoint в
  репозиторий.

Добавлен реестр `backend/voice_engine/voice_models.py`. Он отделяет выбранный
профиль от фактического движка и загружает Silero один раз при первом запросе.
Выбор `jarvis` остаётся первым и default; его фактическая текущая озвучка —
существующий XTTS v2 fallback, пока обученная модель Jarvis не установлена.
Выбор `kesha` направляет синтез в локальный Silero package checkpoint.

В backend добавлены `/voice/models`, `/voice/model` и включение состояния
голосовой модели в `/voice/status`. В существующий раздел “ЗВУК И ВИЗУАЛ”
добавлены выбор модели и фактический статус движка, сохранение выполняется
через QSettings.

## Ограничения

Первый Silero-инференс на CPU занимает несколько секунд из-за загрузки
package-модели; повторные вызовы используют уже загруженный объект. Профиль
Kesha требует локального checkpoint и `torch`; при их отсутствии приложение не
должно падать, а статус должен показывать причину недоступности.

Для голосового runtime выбран баланс скорости и качества `24 kHz` вместо
исходных `48 kHz`; значение можно изменить через `JARVIS_KESHA_SAMPLE_RATE`
(`8000`, `24000` или `48000`). Голосовые ответы ограничиваются 280 символами,
а подтверждающий WAV запускается параллельно с запросом к Ollama. Для
разговорной ветки Ollama получает `num_predict=64`, чтобы длинная генерация не
задерживала речь.
